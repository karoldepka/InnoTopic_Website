# Styling & layout conventions

Observed conventions in this codebase - follow them for consistency rather than introducing a new pattern per component.

- **Syntax**: component styles are `.sass` (indented, no braces/semicolons), not `.scss`. `global.scss` (braces syntax) is the one shared/global exception.
- **Component root layout**: put the component's own flex/grid layout on a `:host` block at the top of the file, not on a wrapper `<div>` inside the template.
- **Spacing between siblings**: prefer `gap` on the flex/grid container over per-child `margin`. Margins are the exception, not the default, in this codebase.
- **Colors**: always via CSS custom properties, never hardcoded hex/named colors - `var(--ion-color-primary)`, `var(--ion-text-color)`, `var(--ion-border-color)`, etc. When a fallback is useful (e.g. the var might not be set in some embed context), provide one: `var(--ion-border-color, rgba(0, 0, 0, 0.1))`.
  - Never use `--ion-color-success` as a text color: it is not guaranteed to contrast with every themed surface. Use `--ion-text-color` for text, and reserve the success token for borders, icons, or backgrounds whose paired foreground has been explicitly checked.
- **This app is dark-mode only** (`html { color-scheme: dark }` in `global.scss`) - there is no light theme to also check, but don't assume "dark" means every neutral surface can just be near-black/near-white:
  - `--ion-color-light` is a **fixed near-white regardless of theme** (`#f4f5f8`) - using it as a background (e.g. a hover/filled state) puts a near-white surface under this app's light/white text, which is nearly invisible. This was a real, shipped bug (GH #139-adjacent contrast fixes, 2026-08-02) in three separate components before being caught.
  - For a subtle, theme-aware neutral surface (hover states, subtle fills, dividers), use the `--ion-color-step-*` scale instead (`--ion-color-step-50` darkest … `--ion-color-step-950` lightest, defined in `src/theme/dark_orange_blue.scss`). `--ion-color-step-150` is the usual choice for a "just slightly lighter than the background" hover/highlight.
  - When adding any new hover/active/selected background, sanity-check the resulting text-on-background contrast before considering it done - don't just trust that "it's a themed color, so it must be fine."
- **Shared box-model for repeated small UI elements** (pills/chips, etc.): centralize the shape (padding, border-radius, font, opacity) in a shared class in `global.scss` and reuse it from each component, rather than each component redefining the same box model independently and silently drifting apart over time. See `.slot-pill` in `global.scss` for the pattern.
  - Watch for a component-scoped stylesheet silently overriding part of that shared shape: Angular's emulated view encapsulation gives a component's own selectors higher effective specificity than an unscoped global class, so e.g. a row/list-item class's `padding-bottom`/`margin-bottom`/`border-bottom` (meant for its own expanded-row layout) can leak through and override just one side of `.slot-pill`'s padding when both classes land on the same element - even though the shared class's shorthand padding declaration looks like it should already own that. Scope the conflicting properties with `:not(.slot-pill)` in the component-local rule rather than letting them leak through (2026-08 incident: `TreeNodeCellsComponent`'s `.slot-cell`/`.slot-cell--compact` vs. `.slot-pill`).
- **Verify vertical centering and spacing, not just structure**: when a flex row uses `align-items: stretch` (or any non-`center` default), a plain block-level wrapper `<div>` around an `<input>` or icon does NOT vertically center its content by default just because the parent stretches it - it needs its own `display: flex; align-items: center`. Don't assume CSS that reads correctly on paper actually renders correctly; check computed alignment/spacing (a screenshot or computed-style check) before considering layout work done, especially for icon+text pills/chips and dense table-like cell rows (2026-08 incidents: `numeric-cell.component.html`'s estimated-time input pinned to the top of its row; a per-row voice-memo/dictation button floating mid-row from sharing `flex-grow: 1` with its title sibling instead of taking a natural width).
- **Spacing values**: use the `--space-*` custom properties defined in `global.scss`'s `:root` (rem-based, Tailwind's default scale/naming: `--space-1` = `0.25rem`/4px, `--space-2` = `0.5rem`/8px, `--space-0-5`/`--space-1-5`/`--space-2-5` for the half-steps, up through `--space-8` = 2rem/32px) instead of a bare px/rem literal in new or edited padding/margin/gap/border-radius declarations. This app favors tight, compact spacing for its dense list/cell UI (`--space-1`/`--space-2`-ish, not `--space-6`+) - match the density of the surrounding component rather than defaulting to something more "spacious".
- **Pills/chips**: `border-radius: 999px` for fully-rounded pill shapes.
- **Icons**: use the solid/filled Ionicons variant - the bare icon name (`name="home"`), not the `-outline` or `-sharp` suffixed variants. Don't reach for the `[ios]="X + '-outline'"` / `[md]="X + '-sharp'"` adaptive-mode pattern seen in some older components (e.g. the side menu) for new icons - it's inconsistent in practice anyway, since the app's global Ionic mode is `md` (`app.module.ts`) but many individual popovers/pages force `mode: 'ios'` locally (grep `mode: 'ios'` - there are a dozen+), so the same suffix pattern silently renders a different style depending on where it's used. A bare solid name always renders the same regardless of mode.
  - **Every icon must be explicitly registered** in `src/app/register-ion-icons.ts`'s `registerIonIcons()` - this app does not auto-register the full Ionicons set. An unregistered `name`/`ios`/`md` icon renders completely blank with no console error or warning, so the failure is silent. This was a real, previously-unnoticed bug that left every side-menu item (including long-standing ones like Home/Search, not just newly-added ones) invisible (2026-08 incident). If a new icon doesn't show up, check this file first before assuming a CSS/layout problem.
